3设计原则（决定成败的四条）

① 原站只读

原目录以 :ro 挂载给新服务，物理上杜绝“手滑改到老代码”。新代码全部放在独立目录 /opt/1panel/www/sites/192.168.1.10/v2 与独立容器里。

② 双跑不切库

不做数据迁移、不改表结构。新前端只“读”和“代理写”，任何时刻旧站单独也能跑。

③ 功能对齐到入口级

以 162 个 .php 入口为验收基线，每一个都要在新前端有明确归属（重做 / 保留跳转 / 后台面板承接），不允许“悄悄消失”。

④ 路由可回滚

新前端挂在 /v2（或独立端口），旧站首页不变。验收通过后再决定是否把 / 指向新版，回滚只需改一行 openresty 配置。

5核心流程

5.1 登录与会话（最容易被忽略、也最容易踩坑的一环）

① 提交
新版登录页 → POST /api/auth/login → BFF 以表单方式请求原站 takelogin.php（含两步验证码、密保问题等全部原字段）。
② 判定
BFF 读取响应：成功时原站会下发 Set-Cookie 会话；失败时从 HTML 里提取错误文案（密码错 / 未验证 / 被封禁 / 需两步验证）原样回传。
③ 托管
会话 Cookie 不下发到浏览器，由 BFF 存服务端（Redis，key = 新版 sid），浏览器只拿新版 HttpOnly Cookie，安全性反而比现在好。
④ 代理
之后每个请求，BFF 用对应会话去请求原站，实现“一个浏览器会话 ↔ 一个 PHP 会话”的映射。退出登录则调用原站 logout.php 并销毁映射。

5.2 种子列表 → 详情 → 下载（最高频路径）

列表
GET /api/torrents?cat=&team=&incldead=&search=&page= → 优先走 L2 接口，缺失字段由 L1 补齐 → 返回统一结构（封面、标题、分类、大小、做种/下载、完成数、促销标签、发布时间）。
详情
GET /api/torrents/:id → 基本信息、简介（清洗后 HTML）、文件列表、评论、做种/下载者、积分与促销状态、举报入口。
下载
下载按钮不直连 download.php（会暴露 passkey），而是 GET /api/torrents/:id/download → BFF 带会话取种子文件 → 以 application/x-bittorrent + 正确文件名流式回传。
Tracker
announce.php / scrape 完全不碰，客户端仍走原地址，做种/下载链路零风险。

5.3 发种与写操作

上传
新版分步表单（选分区 → 填元数据 → 传种子 → 选文件 → 提交）→ 拼成原站 takeupload.php 的字段（含 nfo、descr、technical_info、mediainfo、source_sel…）逐字段对齐 → 校验错误回显到对应步骤。
写操作
感谢 / 收藏 / 评论 / 举报 / 认领 / 兑换 / 签到 / 邀请 / 改密 —— 全部走代理，前端只负责交互与乐观更新。
兜底
代理失败或字段不兼容时，降级为“跳转原站页面”（新窗口打开旧版功能页），保证任何情况下功能都不会消失——这是“功能一个不少”的最终保险绳。

8风险与对策

风险概率对策
HTML 解析随原站升级失效中解析规则与页面结构解耦（选择器集中管理 + 单元测试快照）；原站只读挂载，不会被动升级；异常自动降级为跳转旧页并告警。
写操作字段不兼容中先用 1:1 字段镜像，逐项对齐；预留“跳转旧页”兜底；上线前用测试账号跑一遍全量写操作。
性能反而不如旧站低Redis 缓存 + 列表接口合并请求 + 静态资源 CDN 化；目标：首屏 < 1.5s，列表接口 P95 < 300ms。
双份会话被风控/踢下线低不做双登录；BFF 复用同一 PHP 会话；同时在线设备数与原逻辑一致。
改到原站代码低只读挂载 :ro，物理隔离。
